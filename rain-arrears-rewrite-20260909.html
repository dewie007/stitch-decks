Two integration approaches

Different complexity, different outcomes

Option A: Targeted payment links
Rain builds
  • API to create per-customer consent requests (contract ref, amount, type)
  • Webhook handler for payment confirmation + token storage
  • Billing system update to store and use new tokens
  • Cohort selection logic in collections workflow
Stitch provides
  • Payment link generation API
  • Payment processing + token capture
  • Webhook delivery on payment events
Effort: Significant - billing system changes required
Best for: Repairing specific failed collection arrangements
Option B: Shared hosted page
Rain builds
  • Balance lookup API (real-time outstanding by billing ID)
  • Redirect/placement strategy from existing Pay@ URLs
  • Token storage from webhook
Stitch provides
  • Hosted payment page with method selection
  • Balance polling integration
  • Token capture + webhook delivery
Effort: Lighter - balance API + redirect
Risk: Customers stay on familiar Pay@ links (Andre flagged)
⚠ Blocker: Zubair's integration feasibility assessment is needed before scoping either option. Not yet received - flag for next steps.

Pilot design

Controlled test with measurable outcomes

Structure
  • Two groups: treatment (Stitch link) vs control (existing Pay@ link)
  • Cohort: Cards that succeeded ≥1x but failed last 2+ months
  • Size: 5,000 per group from one billing cycle date
  • Duration: Two subsequent billing cycles after link delivery
  • Primary metric: Cash collected per assigned customer
Targets set after first cycle's data, not before
Measurement
  • Cash collected per assigned customer (treatment vs control)
  • Method capture rate (payment → stored token)
  • Subsequent collection success (cycle 2 and 3 on new tokens)
  • Comms volume change (retry/escalation messages sent)
  • Customer complaints or service calls during pilot
Customer safeguards
  • Preserve opt-out at every step
  • No auto-enrolment in VRP
  • Walled Garden payment restores access immediately
Operational safeguards
  • Existing Pay@ links remain active
  • Manual payers keep current path
  • Rollback criteria defined before launch
Data safeguards
  • Daily reconciliation: Stitch webhooks vs Rain billing state
  • Alert on payment-token mismatch
  • Weekly reporting to both teams

Appendix A2

Evidence gaps

Flagged rather than filled with assumptions

1. Pay@ ↔ billing ID match — Unknown overlap between Pay@ payers and the failed-collection population. Cannot size the opportunity without this.
2. Unique customer count — 626K tokens ≠ 626K customers. True customer count requires Rain billing data. The original deck's "321K cards fail every cycle" conflates tokens with customers.
3. Intentional manual payers — No way to distinguish deliberate preference from necessity without Rain flagging which customers were removed from card runs by choice.
4. Active subscribers in never-collected pool — Unknown how many long-failed tokens represent genuine active subscribers vs stale/churned records.
5. VRP willingness — Capitec Pay@ volume (R 72.2M) shows the Capitec user base but does not prove willingness to consent to recurring debits.
6. Zubair's integration assessment — Not yet received. Required before integration effort can be scoped for either option.
7. DO reversal impact — If debit order collections are in scope, net success rate after reversals may differ significantly from gross (e.g. MTN: 99.9% gross → ~59% net).
