Evidence  Stitch collection data
The collection gap
Rain runs card collections on 626K cards/month. Only 305K collect successfully (49%). The remaining 321K cards fail every cycle - estimated R 213M/month in uncollected subscriptions.
Why collections fail
69% insufficient funds - the card is real, the customer is real, but money isn't there when the batch runs. 12% auth failed. 5% expired card. The problem is overwhelmingly timing and balance, not card validity.
Key distinction
Capitec Pay (R 72M in Pay@) = consumer-initiated bank payment via Capitec app. Capitec VRP = consent-based recurring debit. Rain has only ~150 VRP transactions/month through Stitch (launched Aug 2026). The R 72M shows the Capitec user base that could be on VRP.
Assumption
We do not have Pay@ data matched to billing IDs. The overlap between Pay@ payers and the 321K failed-collection base is unknown. This is a critical data gap for the pilot.
Two approaches to capture payment methods
Targeted links for arrears recovery vs a shared hosted page alongside Pay@
Option A
Targeted Stitch payment links
  • Per-customer link generated from rain's billing system with contract reference, amount owed, and consent type (card or VRP)
  • Replaces ${paylink} in existing SMS/WhatsApp comms for the selected cohort
  • Customer pays arrears and authorises future recurring collection in one step
  • Rain engineering: API integration to create consent requests, handle webhooks, store tokens, update billing
  • Operational: collections team selects cohort; Stitch link inserted into existing comms flow
Best for
Failed recurring customers where rain wants to repair the collection arrangement. Higher conversion expected because the link is personalised with the right amount.
Option B
Shared hosted page with Pay@ alternatives
  • Single hosted payment page that polls billing ID for the current balance (similar to existing Pay@)
  • Offers card, Capitec VRP, and ABSA Pay alongside existing Pay@ channels
  • Customer chooses method; if card or VRP, Stitch captures the token for future collections
  • Rain engineering: lighter - balance lookup API + redirect; less per-customer logic
  • Risk: customers may continue using familiar Pay@ links and never visit the new page
Consideration
Andre noted customers reuse familiar Pay@ links because they persist and show the latest balance. A new URL needs deliberate redirection or prominent placement in comms to get adoption.
Operational fit with rain's existing process
Mapping the Stitch link into rain's current collections workflow
Process steps & changes
1
Select cohort Change
Today: staff select failed-payment cohorts manually. Proposed: add targeting by failure reason (insufficient funds vs invalid card), bank (Capitec = VRP candidate), and arrears pattern (cycling vs chronic). Owner: collections ops + billing team.
2
Send comms Existing
Today: missed-payment SMS/WhatsApp with ${paylink}. Proposed: for eligible customers, replace ${paylink} with Stitch-hosted URL. Fits the existing campaign schedule (1st/15th cohort runs). Measure: delivered → link visit → payment.
3
Receive payment Change
Today: Pay@ confirms immediately, updates balance. Proposed: Stitch webhook confirms payment + token stored. Rain must handle: partial payments, pending payments, and payments through old Pay@ links. Owner: billing/integration team.
4
Update future payment details New
Today: paying and updating recurring card are separate actions. Proposed: combined in one Stitch interaction. Customer explicitly authorises card refresh or VRP consent. Rain stores token for next billing cycle. Key change: this eliminates the separate card-update campaign.
5
Next collection Existing
Rain runs the next monthly collection using the new token. Stitch processes as normal. If the new token also fails, the customer re-enters the standard retry/comms flow.
Manual work that could reduce
  • Separate card-error campaigns - "Invalid Card Error" and "McCode error" comms become unnecessary for customers who update via the Stitch link
  • Walled Garden escalation steps - customers who pay + update their method in one interaction skip the multi-invoice escalation ladder
  • PTP follow-up - if the Stitch link captures a working token, the Promise to Pay cycle is replaced by automated collection
  • Retry volume - rain currently runs 1.8M card attempts/month for 626K cards. Repairing methods at the point of payment reduces failed retries
Assumption  Segment routing
  • Capitec cards failing (170K/month at 37.8% success) → offer Capitec VRP as primary recovery path
  • Insufficient funds on other banks → offer card refresh via Stitch link (new card or retry window)
  • Invalid/expired cards (68K unique) → card-update link with no retry, just fresh tokenisation
  • Intentional manual payers → preserve their Pay@ preference; offer VRP/card backup only if they opt in
Respecting customer choice
Three distinct populations require different treatments - not everyone should move to automated collection
Failed recurring customers
~157K cards
Cycling in and out of arrears
Goal: recover the arrears balance and repair the recurring collection method in one interaction.

Approach: Stitch link replaces Pay@ in the missed-payment SMS. Customer pays, authorises new card or VRP, and automated billing resumes.

Partial payments: accept what the customer can pay; the Stitch link should handle balances correctly and still offer method update.
Manual payers open to automation
~55K cards
Failed collection, paid one-time with same card
Goal: offer an explicit move to recurring collection - only with consent.

Approach: after a successful one-time payment, present the option: "Would you like us to use this card for future payments?" Never auto-enrol.

Consideration: some use low-limit or virtual cards deliberately. The card works once but would fail recurring. Respect that signal.
Intentional manual payers
Unknown
Needs Pay@ data matched to billing
Goal: preserve their preference. Offer a backup arrangement only if they want it.

Approach: leave Pay@ as the primary path. Optionally surface a "set up auto-pay" link in comms - no pressure, no walled-garden consequence.

Reused links: these customers rely on persistent Pay@ URLs that fetch the latest balance. Any Stitch link must be equally persistent and intuitive.
Walled Garden & restricted access
Customers in Walled Garden have limited service. The Stitch link must work within this restricted state - payment restores access. If the customer also updates their payment method, rain should confirm the service uplift immediately, not wait for the next billing cycle.
Outstanding question
How many Pay@ users are genuinely manual-by-choice vs simply lacking a working card on file? This determines the split between segments 2 and 3. Matching Pay@ billing IDs to Stitch collection records would answer this.
Recommendation and pilot design
Start with Option A on a defined cohort, measure four outcomes, then decide on broader rollout
Proposed  Pilot definition
Eligible customers
  • Cycling arrears, Capitec cards - cards that have succeeded at least once but failed the last 2+ months. Offer Capitec VRP via Stitch link
  • Insufficient-funds failures, non-Capitec - cards failing on timing/balance. Offer card refresh via Stitch link
  • Exclude chronic never-collected (362K cards) until we understand how many are truly active subscribers
  • Pilot size: ~5,000-10,000 customers from the 1st-of-month cohort

Required  Data & integration questions
Before we can start
  • Match Pay@ to billing IDs - which of the 321K failed-collection customers already pay via Pay@?
  • Active subscriber count - how many of the 362K "never collected" cards are genuine active subscribers vs stale records?
  • Intentional manual payers - can rain flag customers who were removed from card runs by choice?
  • Billing system capability - can rain generate per-customer Stitch consent requests from their billing engine?
  • Balance lookup API - can Stitch-hosted page query the customer's current outstanding balance in real time?
  • Webhook handling - who builds the payment-confirmation + token-storage flow on rain's side?
